What is MIRA?

MIRA (Modular Interoperable Research Attribution) is a discourse graph ontology for scientific arguments maintained by Marc-Antoine Parent. It defines how scientific claims, evidence, questions, and studies relate to each other as a typed graph. The schema is written in LinkML and generates Pydantic (Python), TypeScript, RDF/OWL, SHACL, and JSON-LD.

It is deployed at 10+ life-science labs (McGill, UW, NYU, QBI) with 6,000+ signed research records. It functions as the inter-lab exchange layer that eLife is now integrating into their article platform.

MIRA is closely related to the Discourse Graph movement (Joel Chan's work, originally built in Roam Research) — the conceptual structure is the same: questions, claims, evidence as first-class nodes with typed edges. MIRA is the formalized, interoperable version of that idea.

Key gap vs HaaK: MIRA does not use CiTO. HaaK has 13 CiTO-aligned edge types (tests, entails, interprets, scopes, rulesOut, replicates, contradicts, extends, qualifies, …) — none of these exist in MIRA natively, though they are proposed for contribution upstream.

Extraction Overlay (mirax)

The MIRA-extraction spec adds operational machinery on top of the core schema for provenance tracking and curation status:

  • SourceSpan — verbatim quote, doc_id, char offsets, page, bbox, grounding status (verified / fuzzy / unverified)
  • Provenance — run_id, model, prompt_id, confidence, raw completion hash
  • EpistemicStatus — hypothesis / claim / assumption / definition / observation
  • ActivityModality — proposed / in_progress / completed
  • CurationStatus — ai_extracted / in_review / expert_verified / rejected
  • Bundles — content-hashed grouping primitive for inter-lab exchange
  • Identity — Agent with ORCID / ROR / DID

How MIRA Relates to eLife / OXA

eLife is building OXA (Open Exchange Architecture, maintained by Curvenote) as their native document format — typed JSON node trees for scientific papers. OXA and MIRA are complementary layers:

  • OXA — document structure (how a paper is represented)
  • MIRA — argument structure (how claims relate to each other and to evidence)

eLife's integration plan: OXA documents contain claim nodes; those nodes export to MIRA JSON-LD for inter-lab exchange. HaaK already has bridge scripts for both directions (export_discourse_graphs.py). The spec.md in home/collabs/mira/oxa-adoption/ describes this convergence, including a vocabulary alignment table.

Paul Shannon's August 27 request is specifically about feeding MIRA-formatted claims into eLife's article reading experience — the platform is ready to consume them; they need the Gädeke claims converted as a pilot.

Converting HaaK → MIRA

The Gädeke paper has 26 claims in HaaK format (YAML-frontmatter markdown in elife-claim-trees/claims/gadeke-2026-guilt-insula/). Converting to MIRA means mapping three things: node types, relations, and status fields.

Role mapping

HaaK ClaimRole → MIRA type Notes
hypothesis mira:Claim (epistemic_status: hypothesis) Direct mapping
prediction mira:Claim (epistemic_status: claim) No prediction concept in MIRA
empirical mira:Evidence Direct mapping
control mira:Evidence MIRA has no control/empirical distinction
methodological mira:Protocol Close but not identical
synthesis / interpretation mira:Claim MIRA has no sub-roles
literature-context dg:SourceDocument Different structural level
scope — No equivalent in MIRA

Relation mapping

HaaK relation → MIRA predicate Loss?
supports mira:supports None
opposes / contradicts mira:opposes Slight flattening
tests, entails, interprets Raw CiTO IRI or collapsed to supports Semantic precision lost
scopes, qualifies, extends No equivalent Drop or annotate as custom property
replicates No equivalent Proposed for MIRA contribution

Practical steps

A conversion script reads each claim's YAML frontmatter, maps the role field to a MIRA entity type, maps relations to MIRA edges, wraps text content as the node's proposition, and serializes as JSON-LD using MIRA's context. The existing export_discourse_graphs.py does most of this already — it needs to be pointed at the Gädeke claim files and the output schema aligned to the current MIRA version Paul's team is using.

The verification step (which Paul specifically mentioned) is confirming that the claim role and relation mappings faithfully represent what the paper argues — the MIRA graph should be checkable against the paper itself.
