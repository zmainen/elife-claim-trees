# The split: a public claim-graph repository and an eLife corpus

*2026-09-13. A plan, not a record — nothing below has been done.*

This proposes dividing `elife-claim-trees` into two repositories: one carrying the format,
the machinery and the standards mappings, with no paper in it; one carrying the eLife corpus,
the site and the collaboration record. It also settles a name, specifies the interchange
format, and says how it supplies `claimloop`, the Scientopia demo that will consume it.

The argument for the division is that the dependency is already one-directional in substance.
The corpus is produced by the machinery and validated against the spec; nothing in the
machinery needs to know which ten papers exist. Two things violate that today, and they are
the whole cost of the split.

The first is `extract/elife_extract/prepare.py`, which is where eLife actually lives: the CDN
URL patterns, the `10.7554/eLife.(\d+)` regex, and the JATS-versus-PDF routing keyed on
whether a DOI is an eLife DOI. Thirty-two references, concentrated in one module. Every other
module in the package mentions eLife only in its name, its environment-variable prefix, or a
comment.

The second is the pair of scripts that exist to feed the site — `article_json.py` and
`corpus_facts.py`.

Everything else is already parameterised. `config.py` resolves its root from
`ELIFE_CLAIM_TREES_ROOT` and `ELIFE_CORPUS_DIR`; `pipeline/layers.yaml` is templated on
`{paper}` throughout — `runs/{paper}/...`, `claims/{paper}/*.md` — and contains no paper slug
and no eLife path except in the single `article_json` layer. The working-tree layout is
already an abstraction over a swappable root. It has the wrong prefix on its environment
variables, and that is most of what needs to change.

## 1. The name

`tree` is wrong, and measurably so. Building the directed graph from `belongings` and the
top-level relation predicates across all twelve papers and excluding the relations declared
symmetric gives **183 cycles, in every paper without exception**. They are not data errors.
They come from converse relation pairs, and the frequency ranking says exactly which:

| antiparallel pair | occurrences | status |
|:---|---:|:---|
| `derived-from` ↔ `entails` | 100 | redundant converse encoding — the same edge, spelled twice |
| `requires` ↔ `scopes` | 64 | documented as intentional in `scripts/relations.py` |
| `requires` ↔ `supports` | 48 | documented as intentional: "one empirical claim commonly carries both" |
| `dissociates-with` ↔ itself | 20 | declared symmetric |
| `interprets` ↔ `supports` | 30 | genuine: an interpretation reads a result that also supports it |
| `entails` ↔ `tests` | 22 | genuine: a hypothesis entails a prediction; the prediction tests it |

(`discrepancy` appeared in that ranking on a first pass and has since been dropped from the
relation vocabulary altogether — see §3.3.)

Only the first is a modelling defect, and the interchange format below fixes it by declaring a
canonical direction. The rest are real: a hypothesis entails a prediction and the prediction
tests the hypothesis, and both directions carry information. Canonicalising the converses
would reduce the cycle count but would not reach zero, because the hypothesis–prediction
mutual relation is a genuine 2-cycle and the `requires`/`scopes` pair is a deliberate one.

So the data is a directed, typed, multi-edged, cyclic graph over propositions. The name should
be **claim graph**, and the repository **`claim-graphs`**.

This is a consolidation rather than a coinage. The term is already in use in the repository's
own prose — `docs/elife-feedback.md` opens "A claim graph is a structured representation of
what a paper asserts and on what grounds" — and it is already the type name in the OXA export,
where the tree of a paper's claims is a `ClaimGraph` node. It is also the word that came up
unprompted when the split was first described. Adopting it changes the label on the box to
match what is written inside it.

Three alternatives and why not. **Discourse graph** is taken: it names Joel Chan's specific
Question/Claim/Evidence/Source formalism, which `standards.yaml` already lists as a mapping
*target*; reusing the name would confuse the thing with one of the standards it exports to.
**Claim lattice** is worse than `tree`, not better — a lattice is a partial order, which is
acyclic *and* carries joins and meets. **Claim structure** (the name of the existing skill) is
topology-neutral and therefore safe, but it is vague in the specific way that would let the
cyclicity go unnoticed again.

Keep `tree` for the thing it correctly describes: a **view**. The per-paper reader display,
rooted at a hypothesis with predictions and results beneath it, is a spanning tree of the
graph, and `pipeline/layers/claim-tree.md` produces the set that view is drawn from. Graph is
the data; tree is one projection of it. The interchange format has a `views` field for exactly
this, so a reader UI never has to rediscover a spanning tree or, worse, hang on a cycle.

### Mechanics

Keep `elife-claim-trees` as the repository it is and bud the new one off. That preserves the
published Pages URL, the site history, the issue history and the collaboration record, and it
means the corpus stays at the link eLife already has. Use `git filter-repo` on a clone,
keeping only the moving paths, so `claim-graphs` inherits the history of `extract/` rather
than starting at one commit; then delete those paths from the original.

Depend on it as a pinned requirement — `claim-graphs @ git+ssh://...@v0.1.0` — not a
submodule. A submodule would make the corpus repository unpleasant for eLife to clone, which
is the one clone that has to be easy.

## 3. `claims.json` — the interchange format

Written as `schema/claim-set-v0.schema.json`. It is a JSON Schema (2020-12), and it has been
validated against the corpus rather than designed in the abstract: converting all twelve
papers out of the authoring form yields **362 claims and 1,051 edges, with 9 schema errors and
11 dangling references** — a 98.1% clean conversion, with the residue concentrated in one
identifiable defect (§3.3).

### 3.1 Shape

```
{ schemaVersion, document{id,doi,title,url,license},
  provenance{generator,generatedAt,reviewed,sourceRun},
  questions[{id,text}],
  claims[{ id, uuid, text, plain?, short?, type, function?, confidence?,
           addresses[], concepts[],
           assertions[{document,doi,stance,locator{panel,section,quote,figureUri},
                       grounds{method,analysis,dataset,datasetDoi},confidence,note}],
           reproductions[{status,by,date,blockedBy,script,figure,note}] }],
  edges[{from,rel,to,note?,by?}],
  views[{id,kind,roots[],follow[]}] }
```

Four decisions worth defending.

**Edges live at the set level, not on the claim.** The authoring form scatters them across
nineteen top-level predicate keys and a `belongings` list, which is why the same relation is
spelled two ways and why the `derived-from`/`entails` redundancy went unnoticed. One `edges`
array makes the graph inspectable in one pass, makes converse canonicalisation a local
rewrite, and is what a consumer actually wants.

**Identity is the proposition, not the document.** `uuid` is stable across sets and across
renames of `id`; `assertions` is a list, so one claim asserted by two papers is one claim with
two assertions rather than two claims. This is already true of the authoring form and is its
most valuable property — it is what makes a claim able to outlive the paper that stated it, and
it is the thing `claimloop` does not have (§6).

**Cyclicity is declared, not implied.** The schema description says the graph is cyclic, says
why, and tells consumers not to assume otherwise. `views` gives a projection any consumer
needing a tree can use, with `follow` naming the relations the walk descends and the rule that
the walk stops at the first already-visited node.

**`provenance.reviewed` is a first-class field.** Its `none` value means every claim and edge
is machine output that no person has checked. The README says this in prose today; the format
should say it in a field, so that a consumer displaying a claim set cannot fail to know.

### 3.2 What the schema cleans up

Three overlapping fields encode two axes, and the declared vocabularies do not match the data:

- `claim-type` has 9 values in use where `vocabulary.CLAIM_TYPES` declares 7 — `methodological`
  (2 claims) and `scope` (2) are undeclared.
- `role` has 9 values overlapping `claim-type` on six of them (`empirical`, `prediction`,
  `hypothesis`, `scope`, `methodological`, `synthesis`).
- `epistemic` mixes two axes outright: `strong`/`moderate`/`tentative`/`weak` on 283 claims,
  but `prediction` or `hypothesis` — a *role*, not a strength — on 79.
- `assertions[].confidence` carries `strong`/`moderate`/`tentative`/`weak`/`N/A`, where
  `vocabulary.CONFIDENCE` declares `high`/`single-source`/`contested`. Complete divergence.

v0 resolves this into `type` (epistemic kind, 8 values), `function` (job in the argument:
`control`, `literature-context`, `alternative`, `methodological` — the cases not implied by
`type`) and `confidence` (strength, one axis). Normalisation happens in the exporter, so the
authoring form can migrate later on its own schedule.

### 3.3 What the conversion found

**`discrepancy` is not a relation.** It was in the relation list on a first pass because it
appears alongside the others as a top-level key. All eight instances in the corpus are
`{type: methodological-gap, explanation: "Paper reports r=0.61, p=0.028 …; script finds r=0.09,
p=0.70 …"}` — a record of the paper disagreeing with a re-run of its own deposited data. That is
a reproduction finding, not an edge between two claims. v0 drops it from the relation vocabulary
(19 relations, not 20) and adds `reproductions[].discrepancy{kind,explanation}`, required when
status is `mismatch` or `partial`. Without it a mismatch is an accusation with no argument, which
matters more here than anywhere else in the format.

This is the clearest argument for validating the schema against the corpus rather than deriving
it from `relations.py`: `relations.py` does not document `discrepancy`, the prompts emit it, and
nothing had checked what shape it took.

**Ten `rules-out` edges point at prose, not at a claim** — in `kammer-2026-foveal-feedback` (4),
`ejdrup-2026-dopamine` (5) and `meijer-2025-serotonin-orthogonal` (1), the target is a sentence
like "differential quantal release size as the explanation for the DS/VS DA difference".
Elsewhere the same construct was promoted to an `alt-*.md` claim file, which is why every paper
has `alt-` claims and only three carry prose targets. `rules-out` is inconsistently encoded; the
fix is to promote those ten, which `scripts/promote.py` already does.

**One `scopes` edge dangles** — `seven-target-trajectories-13-regions-7478-neurons` scopes
`inhibition-fast-excitation-slow`, which exists in `meijer-2025-serotonin-orthogonal` but not in
`meijer-2025-serotonin-additive-r1`, where the edge is written. A cross-version reference, and an
argument for `claimRef`'s `<document-id>:<claim-id>` form: the edge is not wrong, it is
under-qualified.

A fourth, unrelated to the schema: **nine claim files have invalid YAML frontmatter**, because
`write.py` emits `belongings:` followed by `[]` at column zero. Any YAML parser rejects the
block; `schema/to_claim_set.py` repairs it with a regex on the way in. `gray-matter` in the site
build is lenient enough never to have complained, which is why this has been latent.

### 3.4 What tika needs from it

tika already has the consumer side half-built — `SPEC.md` § `claim=KEY` ("the anchored span
asserts claim KEY"), `ANNOTATION_KINDS` carrying `'claim'`, `keyOf` minting a `k`-series — and
renders those marks as blank cards because nothing resolves the key. Four functions close
that, all over one file, none needing eLife, the pipeline, or Python:

| need | from the format |
|:---|:---|
| completion, and does-this-key-exist | `claims[].id` — the same check tika does for bib keys |
| the card body | `claims[].plain` or `.text`, with `.type` |
| the margin lane's context | `edges` filtered on the key |
| coverage: which claims nothing asserts | the claim list as denominator; tika knows the marks |

This is why the interface should be a file and not an HTTP service. tika resolves citations
against a bib file; a network dependency for rendering a mark would be a regression in the
idiom it already speaks, and a liability offline. Three layers, and tika sits on the lowest:

- **Layer 0, the format.** `claims.json` plus this schema. `fetch` and `JSON.parse`.
- **Layer 1, readers.** The Python library (`load`, `ClaimSet.claim`, `.edges`, `.validate`,
  `.export`) and a dependency-free JS reader shipped from the same repository, so it cannot
  drift from the schema.
- **Layer 2, the service.** `api/server.py` as it stands (DOI or PDF → claim set, SSE), plus
  optionally a read-only `GET /claims/{doi}`. tika may *offer* to fetch a set for a DOI the
  user names; it must never need the network to render a mark.

## 4. The source adapter

`prepare.py` splits along one seam. The generic half turns a document into segmented sections,
captions and candidate statements. The eLife half knows that an eLife DOI has JATS at a
particular CDN URL.

```python
# claim_graphs/sources.py — the generic repository defines only this.
class Source(Protocol):
    """Resolves a document identifier to text a reader layer can segment."""

    name: str                       # "elife-jats", "biorxiv-pdf", "file"

    def handles(self, ref: str) -> bool:
        """True if this source can resolve `ref` (a DOI, URL or path)."""

    def fetch(self, ref: str, cache: Path) -> Document:
        """Retrieve and parse. Caches by content, never by URL alone."""


@dataclass
class Document:
    id: str                         # slug
    doi: str | None
    title: str
    sections: list[Section]         # heading, text, ordinal
    captions: list[Caption]         # figure/table id, text, uri
    tables: list[Table]
    references: list[Reference]
    license: str | None
    provenance: dict                # url, retrieved, sha256, parser
```

Sources register by entry point, so the eLife adapter lives in the corpus repository (or in a
small `claim-graphs-elife` package) and is discovered rather than imported:

```toml
[project.entry-points."claim_graphs.sources"]
elife-jats = "elife_claim_trees.sources:ElifeJats"
```

The generic repository ships `file` (a local PDF or XML) and `crossref` (DOI → publisher
landing page → PDF) so it is usable out of the box, and knows nothing about eLife. The
`prepare` layer in `layers.yaml` changes from a command that assumes JATS to one that resolves
a source by `handles()`.

`Document.provenance` carrying `sha256` matters more than it looks: the pipeline's whole
staleness model is content hashes in `runs/<paper>/ledger.jsonl`, and a source that caches by
URL rather than by content would silently defeat it.

## 5. What must not be published

The finding worth stating plainly is that almost nothing here is eLife's confidential
material. `docs/elife-feedback.md` is a document written *for* Pattinson and Collings and is
already shipped as a public PDF on the site; `docs/corpus-assessment.md` audits papers that are
publicly available; the papers are CC-BY and redistributable.

The real exposure is different, and the split is a good moment to contain it: **unreviewed
machine-generated judgements about named papers and named authors.** Specifically
`docs/corpus-assessment.md`, which grades ten named papers for reproducibility ("Repro: Hard");
the `verification/` failure records; `docs/issues.md` and `docs/orchestration-log.md`, which
name the papers where extraction went wrong; `review/evaluation.json`; and `experiments/`.

The README's disclosure — "Every claim here was produced by a language model, and no person has
verified any of it" — is the right disclosure and should stay. But publishing the *format*
requires none of that material, and the generic repository should therefore carry none of it.
Three tiers:

- **Public with the machinery:** format, spec, standards mappings, prompts, layer
  declarations, code, CLI docs, method. Nothing paper-specific.
- **Public but eLife-scoped:** the corpus. Already public, already labelled. The annotation
  layer is unreviewed, which the format now records in `provenance.reviewed` rather than only
  in prose.
- **Not public by default:** the per-paper judgements above, plus `briefs/` and
  `site/public/haak-overview.pdf` (HAAK material on an eLife-facing site). Publishing any of
  these should be a decision, not a consequence of a directory being tracked.

## 6. `claimloop`, and who consumes the standards

`claimloop` is the Scientopia demo of a claims-based science ecosystem, and it has been moved
out of this repository into `zmainen/scientopia`. It is not a competing core and there is no
boundary to negotiate: it is the first downstream consumer of the standards `claim-graphs`
will own, and it was prepared quickly to get the ecosystem shape working rather than to settle
a vocabulary. That makes the direction of supply clear — `claim-graphs` defines the claim
schema and `standards.yaml`; `claimloop` feeds off them.

Being explicit about the differences is still worth doing, because they say what
`claim-graphs` must provide for `claimloop` to be able to stop carrying its own version.

**Identity.** `claimloop` identifies a claim as `player:step:id` — who produced it, in which
step. `claim-graphs` identifies it by `uuid`, with the proposition as the identity: the same
proposition asserted by two documents is one claim with two `assertions`, each with its own
stance and grounds. The ecosystem demo needs provenance-keyed identity because its whole
subject is who claimed what; the format needs proposition-keyed identity because a claim that
outlives the document asserting it is the point. These are compatible — `player:step:id` is a
provenance address, and in v0 it belongs in `assertions[].document` and `edges[].by`, not in
the claim's identity. A claim two players assert is one claim with two assertions, which is
also the answer the ecosystem wants once two players converge on the same proposition.

**Vocabulary size.** `claimloop` declares 10 types and 10 relations; `claim-graphs` has 19
relations in active use after `discrepancy` is removed. The gap is not redundancy: `claimloop`
has no `scopes`, no `validates`, no `rules-out`, and folds `confirms`/`refutes` into
`replicates`/`contradicts`. Those distinctions are ones the corpus makes and uses, so
`claim-graphs` keeps them and `claimloop` can use the subset it needs. A consumer using ten of
nineteen relations is fine; a producer inventing its own ten is what we are avoiding.

**What `claimloop` has that `claim-graphs` should take.** Two things, both discipline rather
than vocabulary. First, `standards.yaml` as a data file that the exporter reads, with the
honest notes included — "cito:confirms is the nearest; it overstates", "no standard node for a
decision as such" — so that a mapping that does not fit says so instead of being forced. This
repository's mappings are prose in `docs/schema-mapping/`, which cannot be read by the
exporter and therefore drifts. Second, `validate()` returning a list of messages rather than
raising on the first, which is what makes a whole-corpus gate usable (and is the shape
`schema/to_claim_set.py` already adopted).

**What stays separate.** `claimloop.claims.validate()` enforces that an answer may cite only
what its request staged — a player cannot refer to what it was not shown. That is a guarantee
about a process, not about a format, and it belongs in the ecosystem, not in the schema. The
same goes for the two process engines: `claimloop` runs a DAG over players' turns,
`scripts/pipeline.py` runs a DAG over one document's layers. Adjacent problems, and no reason
to merge them.

**Order.** None of this blocks the split. Freeze v0 as written, publish the schema at a stable
URL, and let `claimloop` pin it when convenient. The only thing worth doing early is moving
the standards mappings from prose into `standards.yaml` in `claim-graphs`, because that is the
file `claimloop` will read and the one the exporter should read too.
